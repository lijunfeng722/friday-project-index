# Friday 开发协作

让一次 Friday 开发任务覆盖正确的源码、验证和文档范围，并保留使用者的任务边界。

## 先确定任务和仓库

先区分方案、审查、实现和发布请求。只给方案或只读审查时，完成对应输出，不进入写文件、提交或部署步骤。

定位使用者指定的本地仓库，读取对应 AGENTS.md。用 Git 远端确认仓库身份，不依赖作者电脑路径或固定目录名；只查当前工作区和已知克隆，多个实例不猜测目标。定位到元仓库时，读取它的 repos.json 与维护入口。

- Geeprox/Friday：产品界面、API、控制、视觉、技术文档及依赖安装器。
- lijunfeng722/friday-user-guide：用户手册、示例截图、Pages 和维护工具的下载副本。
- lijunfeng722/friday-project-index：跨仓库入口、根目录的日常启停工具及其测试、公共规范与本技能。

ARL 和第三方服务按任务需要及其自身仓库规则处理，不自动套用三个受维护仓库的写入范围。

需要核对完整约定、文档影响、规则同步或交付范围时，读取 [公共开发规范](references/development.md)。该文件是从元仓库生成的便携副本，不单独维护第二套规范。

## 开始变更前先建分支

所有变更任务（包括代码、文档、配置、脚本、Skill、AGENTS.md 和生成副本同步）开始前，先检查并保留已有改动，确认目标仓库的远端主干并获取最新代码，再从该主干最新提交新建本次任务分支。主干名称以远端默认分支或仓库约定为准；禁止直接在 `main`、`master` 或其他主干上开发，也不能从未更新的本地主干或旧任务分支开始新任务。

跨仓库修改前，每个待写入仓库都分别完成上述步骤。原工作区有已有改动或本机专用提交时，使用独立工作树从远端主干建分支，保留原工作区和历史。同一任务的后续工作继续使用本次分支。无法获取最新主干时，先解决同步问题再开始变更；只读方案和审查不要求建分支。

## 实现与验证

沿现有架构完成本次修改，保留目标仓库原有隐私、权限、设备发现和可发布历史约束。先检查工作区已有改动，只暂存本次文件。

新增人工提交和解释性注释使用中文，保留技术名称、工具指令、协议字段、第三方内容及反例测试数据。选择与改动相称的验证；规则工具变化才运行对应工具测试，纯文档执行文档检查。普通测试使用隔离输入，不启动真实摄像头、模型、音频或家电。

在已接入仓库运行 `python3 scripts/check_dev_policy.py check`。需要检查新提交时传入本次明确的基线；不为满足语言格式扫描或重写全部历史。无法验证的结果如实记录。

## 同步文档影响

逐项判断并记录用户文档、技术文档和顶级索引的影响：

- 用户可见的新功能或使用方式变化：更新用户操作步骤、条件、限制与相关 FAQ；界面变化时更新对应示例截图。
- 架构、协议、数据流或部署变化：更新技术文档和必要的 Mermaid 图。
- 仓库职责、依赖、安装或维护入口变化：更新元仓库对应索引和说明。
- 依赖安装器变化：同步 Friday 源码与测试、手册下载副本、许可证与校验清单。
- 日常启停工具变化：在元仓库根目录维护源码和清单，在 scripts/ 维护测试；使用 scripts/sync_service_tools.py 同步用户手册的下载与测试副本，并更新部署说明。
- 纯内部变更：写清无用户文档影响的理由，避免修改无关的用户操作页面。

按各仓库现有入口验证链接、导出手册、构建和公开输入。产品截图使用可重复的示例，真实家庭画面、凭据、规则清单和日志留在私有目录。

## 按授权交付

只有任务包含相应操作时才提交、推送、发布或部署；沿用已有授权，不重复索取已提供的确认，也不把规范当作额外授权。源码只用经过审阅的公开历史推送，避免把本机私有父提交带入公共仓库。

发布文档时确认 Pages 结果；部署时复用原服务与配置，保留规则、权限和暂停意图。服务端口可访问、摄像头有帧、HA 接受请求都不等于实物动作成功。实际设备动作需要本次任务的范围支持，使用者确认的实物结果单独记录。

交付说明列明改动仓库、用户行为、对应文档、实际验证、提交和发布状态，以及剩余未验证范围。实现任务完成后不额外开启服务或扩大设备控制范围。
